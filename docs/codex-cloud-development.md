# Codex cloud에서 Leehu 개발하기

휴대폰에서 작업을 지시하고 Codex cloud가 Leehu 코드를 수정·검증한 뒤 작업 브랜치와 PR로 결과를 공유하는 절차입니다. GitHub를 공유 코드의 기준으로 사용합니다.

## 환경별 역할

| 환경 | 담당 작업 |
| --- | --- |
| Codex cloud | 저장소 탐색, 코드 수정, 테스트, 로컬 브라우저 검증, 변경 검토와 PR 준비를 담당합니다. |
| GitHub | 공유 소스와 변경 이력을 보관하고 PR로 검토합니다. |
| Stella-NUC | Windows 앱, SAP GUI, 기존 로그인 세션, NUC에 저장된 운영 기록이 필요한 작업을 담당합니다. |
| 휴대폰 MCP | 실제 Galaxy 앱을 확인하고 조작합니다. |

클라우드 개발과 로컬 브라우저 검증에는 Aside·Tailscale·NUC 연결이 필수가 아닙니다. NUC·휴대폰 제어는 실제 연결을 확인한 뒤 수행합니다. Aside CLI 로그인과 NUC 원격 제어 권한은 별개입니다.

## 작업 시작

1. `git status --short`, `git branch --show-current`, `git rev-parse HEAD`로 기존 작업을 확인합니다.
2. 선택한 원격 브랜치를 fetch하고 원격 SHA와 로컬 HEAD를 비교합니다. 새 작업의 기준 브랜치를 지정하지 않았다면 main을 기준으로 하되, 진행 중인 작업의 브랜치는 유지합니다.
3. 일반 개발은 `codex/<작업명>` 브랜치에서 진행합니다. 기존 변경·로컬 전용 커밋을 보존하고 자동 reset·clean·stash를 하지 않습니다.
4. 요청을 문제·변경 범위·완료 조건으로 정리하고 구현합니다. 별도 worktree는 사용자가 요청했을 때만 만듭니다.

## 검증 명령

저장소 루트에서 Python 3.12 이상과 Git을 사용합니다. 기본 검사에는 외부 Python 패키지가 필요하지 않습니다.

```bash
# 작업 중 HTTP 공개 범위·작가 정보·색인 정책·IndexNow 회귀 검사
python3 scripts/check_dev.py

# 반영 전 전체 기존 테스트와 결과 파일
python3 scripts/check_dev.py --suite full --report /tmp/leehu-check.json

# 웹 화면을 수정했다면 데스크톱·모바일 Chromium 검증도 추가
python3 scripts/check_dev.py --suite full --browser --report /tmp/leehu-check.json

# 문학노트 산출물 수량과 정책 확인
python3 scripts/literature_batch.py verify

# 필요한 경우 파일 기반 SEO 감사
python3 scripts/naver_seo_audit.py --out /tmp/leehu-seo-audit.md
```

`check_dev.py`는 명령의 실제 종료 코드를 기록하고 하나라도 실패하면 실패로 종료합니다. 테스트용 게시판·문학노트 저장 경로는 임시 디렉터리로 지정해 `/data` 쓰기 권한이 없는 환경에서도 실행합니다. JSON 보고서는 저장소 밖에 작성합니다. 전체 테스트에는 기존 생성기의 재실행·산출물 동일성 검사도 포함되므로 기본 검사보다 오래 걸리며, 실행 뒤 git diff로 산출물 변경 여부도 확인합니다. 배포·검색엔진 제출은 실행하지 않습니다.

각 검사에는 기본 600초 제한을 적용하고, Linux unittest 프로세스에는 기본 4GiB 주소 공간 제한을 적용합니다. 시간 초과는 종료 코드 124, 메모리 제한으로 인한 실패는 해당 검사 실패로 기록합니다. 필요한 경우 `--timeout 1200 --memory-limit-mb 8192`처럼 조정할 수 있으며, 제한 때문에 중단된 검사를 통과로 보고하지 않습니다. Chromium에는 이 unittest 메모리 제한을 적용하지 않습니다.

브라우저 검사에는 Playwright Python 패키지와 Chromium이 필요합니다. 환경에 없다면 `python3 -m pip install playwright` 후 `python3 -m playwright install chromium`으로 준비합니다. 운영체제 라이브러리 설치 권한이 필요한 경우 해당 환경의 설치 절차를 따릅니다. 시스템 Chromium은 자동 탐지하고, 다른 위치는 `CHROMIUM_EXECUTABLE`로 지정합니다.

`browser_smoke.py`는 임시 로컬 서버에서 홈페이지·작가·작품·공식 링크·문학노트를 1440px와 390px 너비로 엽니다. HTTP 200, 제목·본문, canonical, 내부 링크 이동을 검사하고 외부 네트워크 요청은 차단합니다. 실제 NUC의 로그인 상태, 모든 화면의 시각적 완성도, 운영 배포 성공은 별도 검증 대상입니다.

문학노트를 추가·수정할 때는 기존 README와 AGENTS의 발행 절차를 따릅니다. 기대 수량을 현재 원본에서 확인하고 필요한 정적 빌드를 실행합니다. NUC 운영 기록이나 배포 확인이 필요한 단계는 해당 연결 상태와 실제 수행 여부를 구분해 보고합니다.

## 커밋·PR·배포

- 이번 작업의 파일만 선택해 커밋하고 작업 브랜치에 푸시합니다. 일반 개발은 PR로 공유하며 main 병합과 배포를 구분합니다.
- PR에는 문제와 바뀐 동작, 검증 명령·결과, 남은 제한을 적습니다. 인증·권한 오류로 PR 생성이 막혀도 로컬 커밋과 브랜치를 보존합니다.
- 배포 요청이 있는 작업은 정해진 배포 경로와 해당 버전의 공개 응답까지 확인합니다. 현재 저장소에서 확인되지 않은 CI/CD를 설치되어 있다고 가정하지 않습니다. `.github/workflows`는 기존 규칙에 따라 수정하지 않습니다.
- 작업 브랜치 게시만으로 운영 사이트가 변경되었다고 보고하지 않습니다. 이 안내에는 새로운 자동 배포나 예약 실행을 설치하지 않습니다.

## 휴대폰에서 바로 사용할 요청 예시

| 목적 | 요청 문장 |
| --- | --- |
| 기능 개발 | “Leehu에서 ○○ 기능을 추가해 줘. 완료 조건은 △△야. 관련 테스트와 전체 검증 후 작업 브랜치·PR로 정리해 줘.” |
| 오류 수정 | “Leehu에서 ○○할 때 △△ 오류가 나. 원인을 재현하고 회귀 테스트를 포함해 고쳐 줘.” |
| 화면 개선 | “Leehu의 ○○ 화면을 모바일에서 개선해 줘. 기존 콘텐츠와 canonical을 보존하고 브라우저에서도 확인해 줘.” |
| 코드 리뷰 | “이 PR에서 실제 장애 가능성과 회귀를 검토하고, 근거가 있는 문제를 파일 위치와 함께 알려 줘.” |
| 병렬 작업 | “A와 B를 독립 작업으로 병렬 진행해 줘. 브랜치·담당 파일을 나누고 통합 후 전체 검증해 줘.” |
| 이어서 작업 | “앞선 ○○ 작업을 현재 브랜치에서 이어서 완료해 줘. 기존 수정과 커밋은 보존해 줘.” |

작업을 작게 나누면 검토와 재시도가 쉬워집니다. 진행 중 지시가 바뀌면 현재 작업에 반영하고, 완료된 단계를 다시 실행하기 전에 결과를 확인합니다.

## 완료 보고

결과에는 변경된 동작, 통과·실패·미실행한 검사, 브랜치·커밋·PR, 배포 여부와 남은 작업을 간결하게 적습니다. 기존 문제로 검증이 실패하면 이번 변경과의 관련성을 명시합니다. 토큰·비밀번호·로그인 파일은 Git과 보고서에 넣지 않습니다.

개발 도구 도입 시 확인한 검사 범위와 기존 전체 검사 문제는 [검증 결과](cloud-verification-status.md)에 기록했습니다.
